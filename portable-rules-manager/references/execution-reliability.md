# 规则执行可靠性

用于规则准入、精简、发布验证和失败复盘。不要把本参考全文复制进项目常驻规则。

## 准入与归属

先问：它解决了什么可观察的问题？是否反复适用？谁或什么证据确认了它？适用边界在哪里？如何判断违反？

| 内容 | 归属与处理 |
| --- | --- |
| 用户确认的长期工程约束 | 最小作用域的 `.ai-rules` 正文 |
| 现有代码做法、启发式扫描结论 | 取证材料；确认其合理性后才能成为规则 |
| 功能意图、探索方案、文案、一次性界面设计 | 需求或规格；规则仅引用稳定的工程边界 |
| 可机械判断的约束 | 优先引用项目已有测试、静态分析或构建检查；文本解释原因与修复方式 |
| 操作方法、长示例、外部手册 | 按需参考资料，不常驻注入 |
| 会话进度、未完成任务 | 项目已有工作记录，不混入规则正文 |

不为统一规则而引入固定开发顺序、强制多智能体、固定规划轮数或额外基础设施。新增检查代码须属于用户授权范围；本技能默认只管理规则及检查引用。

## 最小上下文

- 根入口只保留全仓有效、经确认的约束及索引。细节按真实目录归属；全仓规则没有价值时不为了凑分类保留。
- 查重先读清单和候选摘要，再读取有关正文；需要全量语义审查时分批处理并记录覆盖范围，不把未读规则当作已检查。
- 已由工具、类型系统或检查脚本可靠执行的要求，正文保留必要的原因、入口与失败处理，不重复整份规范。
- 不以固定字数作为质量门槛。可比较根入口与受影响目录的实际字节数、规则数量及重复内容；字节数不是模型 token 数，也不代表运行时实际加载量。
- 各适配器可能自动加载正文。根索引是定位入口，不能将其存在等同于加载成功或严格按需加载。

## 验证分层

| 层次 | 方法 | 结论边界 |
| --- | --- | --- |
| 发布完整性 | 发布前空正文和骨架检查 | 仅发现确定的未完成内容，不证明语义质量 |
| 文件一致性 | `check --tools <工具>` | 生成内容与当前源一致，不证明已加载 |
| 作用域 | `explain` 检查命中及不命中路径 | 管理器声明的作用域正确，不等同客户端加载 |
| 工程行为 | 已存在且适用的测试、静态检查、契约检查 | 对明确约束给出客观结果，不覆盖全部业务正确性 |
| 智能体行为 | 当前工具的新会话或隔离环境执行代表任务 | 只证明被测环境与案例；记录工具版本，不能泛化为所有平台保证 |

行为案例至少覆盖被修改约束的正常触发与不应触发场景。涉及例外、冲突、回写或禁用时再补对应案例，避免给简单文案修改强加完整测试矩阵。

评估看实际文件、检查输出与副作用，不以智能体自述或复述规则作为通过证据。比较改动前后使用相同任务、原始文件与权限；模型波动明显时重复试验并保留失败，不能只选成功样本。未能运行就标记“未验证”，不能填成通过。

## 反馈与退役

1. 保存最小失败证据：任务、相关规则 ID、输入路径、预期行为、实际结果及复现条件。沿用项目工作记录，不创建第二套记忆库。
2. 定位原因：未加载先查入口；误命中先修范围；冲突先明确权威与例外；有客观判据却漏检则连接已有检查；产品理解错误返回需求澄清。
3. 选择最小修正：删重、缩小范围、重写歧义或补检查，优先于增加禁令。未经确认的推论保持禁用。
4. 重跑原失败案例及相关反例，观察误拦截和上下文成本。若结果变差，回退本次变更。
5. 当依据失效、架构替换或规则被更明确规则覆盖时，评估合并、降级或退役。没有观察到失败不等于规则无用。
6. 禁用源规则后先预览生成差异并检查旧入口残留；默认同步不保证删除旧文件。实际删除或 `--prune` 仍需明确授权。未清理残留就不能声称旧约束已完全退役。
