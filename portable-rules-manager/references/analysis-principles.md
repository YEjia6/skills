# 分析原则（analysis-principles）

约束「从项目事实推导规则」的分析行为：规则体系生成流程的全部取证、分类与准入判断，以及新增业务含义类规则前的业务确认，都按本文件执行。三条原则共同作用：不得把推测当成已确定的业务规则，不得把当前代码实现直接当成正确的业务定义。

本文件是分析方法；准入与退役流程见[执行可靠性](execution-reliability.md)，正文编写标准见[编写规范](rule-authoring.md)。三者互补，不互相替代。

## 原则 1：以项目实际情况为依据

业务含义只来自项目实际情况。优先分析以下材料，按可得性与相关性选用；关键结论需要两个以上来源交叉验证：

| 顺序 | 分析对象 | 取证重点 |
| --- | --- | --- |
| 1 | 项目目录结构 | 模块边界、分层归属、业务域划分 |
| 2 | 数据库表结构和字段 | 主外键、唯一约束、状态字段、语义字段 |
| 3 | Entity、DTO、VO、Mapper | 字段含义、对象映射、持久化口径 |
| 4 | Controller、Service、Impl | 入口校验、事务边界、编排顺序、计算口径 |
| 5 | 业务接口和第三方接口 | 契约字段、回调、幂等、失败与补偿 |
| 6 | 配置文件及 YAML | 业务开关、多环境差异、外部服务选择 |
| 7 | Redis 缓存实现 | Key 设计、TTL、失效与更新时机 |
| 8 | 定时任务、消息消费和事件监听 | 触发条件、重试、补偿、幂等消费 |
| 9 | 前端页面、表单和交互逻辑 | 字段级校验、按钮权限、提交流程、状态展示 |
| 10 | 已有项目文档 | 需求、设计、接口文档；记载内容必须与实现核对 |
| 11 | 单元测试、集成测试和接口测试 | 断言即规格；测试覆盖不等于实现正确 |

硬性要求：

- 不能只根据类名、方法名或注释判断业务含义。命名与注释只是线索，结论必须有调用链或数据佐证。
- 需要追踪完整调用链：入口 → 校验 → 服务编排 → 持久化/缓存/外部调用 → 返回与副作用，弄清实际数据如何流转、指标如何计算、最终产生什么业务结果。
- 追不到的链路（入口缺失、动态分发、跨仓库）记录已查范围与缺口，不编造补齐。

## 原则 2：区分现状、目标和推测

每条梳理出来的规则必须标注证据状态，写在正文「适用范围」章节（`new-rule` 骨架已含该行）。状态只反映证据强度，不改变规则的 layer 与 strength。

| 状态 | 判定标准 | 处理 |
| --- | --- | --- |
| 已验证 | 有代码、数据库、接口或测试证据支持 | 可按准入流程进入规则源 |
| 已记录但未验证 | 已有文档或需求说明，尚未通过实现验证 | `enabled:false` 待审；列出验证路径 |
| 合理推断 | 通过代码逻辑推导得出，缺乏明确业务依据 | `enabled:false` 待审；写明推断依据 |
| 待确认 | 现有代码和资料不足以确定业务含义 | 列入待确认问题清单，保持禁用 |
| 建议新增 | 为解决架构问题或业务缺口提出的新规则 | 先与用户确认意图，再走创建流程 |

硬性要求：

- 不能把推测当成已经确定的业务规则。「已记录但未验证」「合理推断」「待确认」一律 `enabled:false`，只出现在待确认清单或禁用候选中。
- 不能将当前代码实现直接视为正确的业务定义。实现可能包含缺陷、历史妥协或未完成改造；先确认业务意图，再决定固化规则、提出修正建议或升级为待确认问题。
- 状态随证据变化更新：文档与实现核对一致才能升级为「已验证」；依据被替换或失效的规则按执行可靠性的退役流程处理。

## 原则 3：区分三种规则

候选规则按 BR / FR / TR 分类整理，各自独立记录，不混写：

### A. 业务规则 BR（Business Rules）

回答：业务对象是什么？业务对象之间有什么关系？什么条件允许或禁止某种业务行为？业务指标如何定义？数据如何计算？业务状态如何变化？多个模块之间需要保持什么业务约束？

示例：设备必须归属于指定租户；一条产线可以关联多台设备；产线运行状态由指定的核心状态设备提供；已支付订单不能直接取消；设备运行时间按有效运行状态区间计算。

### B. 功能规则 FR（Functional Rules）

回答：系统提供什么功能？用户如何操作？系统如何响应？哪些数据可以新增、编辑、删除？查询条件和查询范围是什么？操作成功或失败后有什么结果？功能之间如何调用和协作？

示例：用户可以为产线指定核心指标设备；用户可以查询指定日期的设备停机片段；系统支持导出停机片段 Excel；用户可以录入生产工单信息并发起 OEE 计算。

### C. 技术实现规则 TR（Technical Rules）

回答：使用什么技术实现？数据如何存储？接口如何调用？缓存如何设计？系统之间如何通信？多租户如何隔离？异常如何处理？

示例：使用 YAML 配置选择 DPL 或 IOT 服务；Redis Key 必须包含 tenantId；使用统一数据源适配接口；采用 MQTT 或 API 获取设备数据。

硬性要求：

- 技术实现规则单独记录，不能混入业务规则和功能规则。一条正文同时出现业务因果与技术手段时，拆成 BR 与 TR 两条并互相引用。
- 分类与 layer/anchor 正交：BR/FR/TR 描述规则内容，layer/anchor 描述作用范围，互不替代。落盘建议：BR 放 `business/`，FR 放 `features/`（UI 交互规范属于 FR），TR 放 `domains/<技术域>/`，跨模块底线放 `core/`。
- ID 不强制携带类型前缀；分类写入规则标题与 description，保证 rules-index 与 docs/rules 索引可读。
