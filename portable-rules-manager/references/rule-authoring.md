# 规则编写规范手册（rule-authoring）

本手册约束「创建/修改 `.ai-rules` 规则」这一行为本身，是 `new-rule` 骨架的填写标准，也是人工审查规则质量的依据。覆盖两类规则：

- **编程行为规则**：代码风格、持久层、事务、权限、目录约定等约束 AI/人写代码的行为。
- **工程流程规范**：PRD 先行、契约先行、阶段门禁、文档同步等约束开发流程的行为。

两类规则的编写标准相同；区别只在 `layer` 与 `anchor` 的选择。

## 一、规则 ID 命名

- 格式：`[A-Z][A-Z0-9-]*`（脚本强制校验），大写字母/数字/连字符。
- 结构：`<域>-<主题>[-<范围>]`，从大到小。示例：
  - `CORE-ENGINEERING`（全仓库工程底线）
  - `WEB-ANALYTICS-APPS-WEB`（apps/web 的图表分析场景）
  - `BACKEND-JAVA-EAM-BOOT`（eam-boot 模块的 Java 后端约定）
- ID 决定生成文件名（`ai-<id小写>.md/.mdc`），改名等于删旧建新，谨慎。
- 禁止：以工具名命名（规则面向项目，不面向某个 AI 工具）；多个 ID 表达同一约束。

## 二、layer 与 anchor 选择

| layer | 语义 | anchor 要求 | 示例 |
| --- | --- | --- | --- |
| `core` | 全仓库不可牺牲的工程底线 | 必须 `.` | 不得虚构运行结果、不可逆操作需确认 |
| `domain` | 技术域要求（某前端/后端/移动端模块） | 指向该技术域的独立目录 | eam-boot 后端约定、eam-vue 前端约定 |
| `scenario` | 功能场景偏好，只替代相关一般偏好 | 指向该场景的独立目录 | 图表分析页视觉、表单分栏 |
| `local` | 更小的目录局部规则 | 指向具体子目录 | 某个迁移脚本目录的临时约束 |

- `anchor` 必须是**真实存在的独立目录**；`.` 仅限 core。
- 没有独立目录就先整理目录，不要用宽泛 anchor + `excludes` 抵消（v1 直接拒绝）。
- 场景化规则只替换相关偏好，不得取消安全、数据准确性等工程底线。

## 三、strength 语义

- `must`：违反即缺陷，验收不通过。
- `should`：默认遵守，偏离需在交付说明里给出理由。
- `may`：可选偏好，不做验收。

strength 是清单治理字段，不是模型内建优先级；真正起约束作用的是正文里 MUST/SHOULD/MAY 的措辞。

## 四、正文结构（标准章节）

```markdown
# <业务意图命名的一句话标题>

## 适用范围

- 作用域：本规则由 manifest 的 anchor/globs 决定，此处只写人读的场景说明，不写与 anchor 矛盾的范围。
- 触发条件：什么任务/改动场景下适用。

## 规则

- MUST：不可违反的约束，写清因果（为什么），必须可被客观判定违反。
- SHOULD：默认遵守，偏离需说明理由。
- MAY：可选偏好。

## 禁止事项

- 明确边界，防止歧义执行。

## 验收

- 如何检查规则被遵守：审查点、命令、正反案例。
```

极短的 core 底线允许平铺列表（参考 `core/engineering.md`）；domain 及以下一律用章节式。

## 五、条目写法要求

1. **可执行、可检验**：禁止「尽量」「注意」「合理使用」这类无法判定违反的措辞。写「禁止灰显可点击状态，必须隐藏」，不写「注意权限按钮的可用性」。
2. **一条一事**：一条规则只说一个约束；多条约束拆多条。
3. **因果链**：关键约束写明为什么，防止后被误改。例如「禁止单列表 code 唯一索引，因为多租户下 (tenant_id, code) 才唯一」。
4. **例外明确**：允许偏离的条件直接写在条目里。
5. **技术事实以构建文件为准**：版本号、框架、命令必须与 `pom.xml`/`package.json` 等一致，禁止凭扫描猜测填写。

## 六、manifest 登记规范

- `file` 相对 `.ai-rules/`，必须实际存在，`.md` 后缀。
- `globs` 固定为 `anchor/**/*`（根目录 `**/*`），v1 不支持自定义 glob。
- `excludes` 必须为空；需要排除就拆分目录或禁用规则。
- `enabled:false` = 待审候选，不参与任何同步。
- `conflict_group` 只用于互斥场景（如两种视觉模式）；同组启用规则的目录重叠会被拒绝。

## 七、反模式（已验证教训）

1. **宽泛 globs + excludes 抵消**：无 exclude 语义的工具（如 Trae）会全量加载，规则误伤无关目录。
2. **历史事故禁令堆砌**：一次事故先作为候选规则人工审核，不得永久追加全局绝对禁令。
3. **同一约束多处重复**：core 只进根 `AGENTS.md`；Trae 同时加载 `AGENTS.md` 与 `.trae/rules/`，重复加载同一条规则浪费上下文且易产生漂移。
4. **不可执行表述**：「尽量保持代码整洁」无法验收，必须改成可判定的约束。
5. **把扫描猜测当事实**：`scan` 的模块识别是启发式，技术栈、测试命令、架构判断必须人工核实后写入。
6. **工具私有经验写进通用层**：某项目专属约定（如具体表名、具体权限编码）只能放在 anchor 限定到该项目目录的 domain/local 规则里，禁止上浮 core。
7. **规则只写约束不写验收**：没有验收条款的规则无法闭环，等于没有规则。

## 八、合格规则示例

### 编程行为规则（多租户持久层，已验证实践）

```markdown
- MUST：业务表必须带 tenant_id 字段，并使用 (tenant_id, code) 联合唯一索引；
  禁止单列表 code 唯一索引——多租户下不同租户允许同 code，单列唯一会导致跨租户建号失败。
- MUST：租户隔离由 TenantLineInnerInterceptor 自动注入 SQL，手写 SQL 禁止显式拼接 tenant_id = ?。
```

### 编程行为规则（按钮级权限，已验证实践）

```markdown
- MUST：按钮级权限使用 v-auth="'perm:code'" 指令，缺少对应权限点时自动隐藏。
- 禁止灰显可点击状态（disabled 或 disabled + 可见），必须隐藏——灰显会让用户误以为功能不可用而非无权限。
```

### 工程流程规范（阶段门禁）

```markdown
- MUST：开发顺序固定为 PRD → Backend → Frontend → Mobile；禁止前端先行开发，
  因为接口契约由后端 API Contract 唯一决定，前端先行必然返工。
- MUST：每个阶段通过 Gate 验证（编译+测试+API 一致性）才能进入下一阶段；
  未通过则停止开发、输出问题清单。
```

## 九、创建完成自检清单

- [ ] ID 符合命名规范且全局唯一（`grep` manifest 确认）
- [ ] anchor 目录真实存在；非 core 规则未使用 `.`
- [ ] 每一条 MUST 都能被客观判定违反
- [ ] 禁止事项与正向规则不矛盾
- [ ] 与现有规则无重复、无冲突（通读 `.ai-rules/**/*.md`）
- [ ] 技术事实与构建文件一致
- [ ] `sync --tools <当前工具>` 预览符合预期，`check` PASS
- [ ] `explain <示例路径>` 确认作用域正确
- [ ] 新会话正反案例实测通过
