# 可移植规则管理器

目标：让当前任务得到必要且有证据的约束，并验证规则的发布、作用域与实际效果。保留 `.ai-rules` 唯一来源；默认只服务当前会话工具。本技能不改变平台指令优先级，也不代替项目开发流程。

## 按任务读取

- 新增、精简或评估规则：先读 [执行可靠性](references/execution-reliability.md)，需要编写正文时再读 [编写规范](references/rule-authoring.md)。
- 从项目梳理业务规则或生成规则体系：先读 [分析原则](references/analysis-principles.md)；取证材料、证据状态与 BR/FR/TR 分类以该文件为准。
- 同步、切换工具或排查加载：读 [工具适配](references/tool-adapters.md) 中当前工具一节；修改清单时读 [清单格式](references/SCHEMA_AND_COMPATIBILITY.md)。
- 仅检查漂移或回写：直接使用下方对应流程，不强制进行全仓扫描和业务分析。
- 完整命令示例见 [操作手册](README.md)。不要一次加载全部参考文件。

## 先明确问题和边界

1. 从当前会话确认目标、授权范围与验收结果；信息已经明确时不要重复询问。模糊的规则优化先明确失败现象、违反后果和期望效果，再反馈因果链与边界。
2. 确认项目根目录（优先 Git 根）和当前工具身份。Codex=`codex`、Cursor=`cursor`、Claude Code=`claude`、Gemini CLI=`gemini`、Copilot=`copilot`、Windsurf=`windsurf`、Trae=`trae`、DeepSeek Harness=`dsh`。身份不明时询问；目录痕迹只能用于交叉验证。
3. 读取清单、根入口及相关作用域规则，定位重复、矛盾、失效依据或验证缺口。技术事实以构建配置及源码为证；代码现状不能自动升级为必须遵守的规范。
4. 先修已有规则，只有无法表达独立约束时才新增。纯产品意图、探索性功能、文案、一次性界面设计进入需求或规格，不进入长期工程约束。

## 创建规则流程

所有命令均使用 `python <skill_dir>/scripts/rules_manager.py --project <repo> <命令>`。

1. 按需 `detect` / `scan` 只读探测；扫描结果是候选，不能据此编造架构、权限或测试命令。已有明确作用域时无需全仓扫描。
2. 需要建立统一来源时执行 `init`；已有清单不覆盖，历史 Markdown 默认作为禁用候选。检查初始化模板，只保留对本项目有价值的条目。
3. 先确认规则的触发条件、因果、最小作用域、例外及验证方法。业务含义以调用链和数据佐证，不能只凭类名、方法名或注释（分析原则 1）；未确认的业务决策使用 `enabled:false` 待审并标注证据状态（分析原则 2）。
4. 用 `new-rule --id <规则ID> --file <相对源路径.md> --anchor <目录> --layer <层级> --strength <强度> --description "说明"` 生成骨架，待审规则加 `--disabled`。
5. 填写正文并删除骨架提示和占位内容。每条必须约束都有可观察的违反条件；能用已有测试、静态分析或构建检查验证的，引用真实入口。规则正文中的命令不自动获得执行授权。
6. `sync --tools <当前工具>` 预览；确认结果符合任务范围后加 `--apply` 发布。已有授权内的正常发布无需逐条再次询问；遇到手写文件冲突先审查，不擅自强制覆盖。
7. `check --tools <当前工具>` 检查文件一致性；`explain <命中路径>` 与 `explain <不应命中路径>` 检查作用域。按改动风险执行行为案例；未运行的验证明确报告。

## 规则体系生成流程

用户要求从项目整理完整规则体系时：

1. 先看目录、构建入口、已有规范与规则索引，再按业务边界分批取证；不默认通读全部代码。取证材料与调用链要求按[分析原则](references/analysis-principles.md)原则 1：优先以表结构、Entity/DTO/Mapper、Controller/Service/Impl、接口契约、配置、缓存、异步任务、前端与测试交叉验证，不能只凭类名、方法名或注释断业务含义，追不到的链路记录缺口。记录覆盖范围与未查模块。
2. 候选按业务规则 BR、功能规则 FR、技术实现规则 TR 三类整理，技术实现规则单独记录（原则 3）；每条标注证据状态：已验证 / 已记录但未验证 / 合理推断 / 待确认 / 建议新增（原则 2）。只有已验证且具有持续价值的约束进入规则源；其余引用既有需求、规格或文档，避免重复复制。
3. 对候选执行准入判断，优先合并重复内容；「已记录但未验证」「合理推断」「待确认」保持禁用，跨模块冲突与业务缺口列入待确认清单，「建议新增」先确认意图。不得为了规则作用域迁移业务目录。
4. 按创建流程落地。根入口保留精简的公共约束与索引；领域细节放最小适用目录。生成器仍按适配器原生机制输出正文，不能声称所有工具都支持严格懒加载。
5. 需要人读文档库时 `export-docs` 预览后 `export-docs --apply`。`docs/rules` 是派生文档，不是第二权威来源；不要求所有项目生成。
6. 多工具仅限用户明确点名；对每个实际同步的工具分别执行 `check --tools <工具>`，不能只检查最后一个。

## 回写与切换

- `harvest --tools <单个工具>` 先预览，核实后加 `--apply`。源文件和被覆盖的生成文件先备份，回写后重渲染当前工具，再执行 `check`。
- `HARVEST` 是可回写正文；`ORPHAN` 是规则块外手改，`UNKNOWN-RULE` 是未知 ID，两者不得自动回写。`INDEX-DIFF` 是索引落后，重新同步即可。
- 回写会重渲染：若存在 ORPHAN/UNKNOWN-RULE，先向用户呈现可能被覆盖的内容并确定保留方式；备份不是静默覆盖的理由。
- 切换工具时从 `.ai-rules` 向新工具预览并同步。保留旧工具文件；删除需要明确授权。

## 执行边界

- `sync` / `harvest` / `check` 显式指定 `--tools`；默认只处理当前工具。`harvest` 只接受单个工具。
- `--force`、`--prune` 需要明确授权；禁止覆盖符号链接或逃逸项目的目录联接。
- 只编辑 `.ai-rules` 源；生成入口的手改走 `harvest`。根索引与 `docs/rules` 由生成器维护。
- v1 的 globs 固定为 `anchor/**/*`（根为 `**/*`），启用规则不能用 excludes；没有可表达的作用域就保持禁用并报告限制，不自行重构业务目录。
- 空正文、未完成的工具骨架不得发布。脚本仅拦截确定的空正文和本工具占位内容，不验证自然语言语义、不保证模型服从。
- 检查共享入口和专用入口是否重复加载。治理层级与 strength 不是模型指令优先级，局部偏好不能取消工程底线。
- 仅修改指定项目中的规则与必要配置；不修改业务代码、全局权限，不安装依赖、不调用模型接口。适配器变更须核对当期官方资料并测试。

## 验证与反馈

报告实际修改的规则及原因、作用域正反例、执行过的检查和结果、未验证项与待确认决策。同步通过、作用域正确、行为通过分别描述。

出现失败时先区分未加载、范围错误、内容冲突、缺少检查或任务理解错误，再修改对应环节。沉淀可复现案例；不因一次失败永久增加全局禁令。依据被替换、作用域消失或与现有检查重复的规则应合并、降级或退役，具体流程见执行可靠性参考。
